# 夸克网盘监控：从「每轮整棵列」改成「先问指纹，只列变了的目录」

2026-10-14 用户问「夸克没有目录树，每次列目录是不是太不优雅」之后定的方案。病根不在没有目录树（115 的整树导出也是全量，
115 监控靠的是生活事件流），而在没有增量信号。真机实测后确认夸克的目录元数据够用：每轮先批量问一遍每个目录的指纹，
只列指纹变了的目录，后面的对比、事件、阀门全部沿用。**方案先给用户看，同意后再动手。**

## 现状（逐条核过代码）

**机制**：快照源 `services/life/sources/quark.ts`。每轮把账号下每个任务的 `originPath` 整棵列一遍（`:237` 取根、`:243` 调
`walkSubtree`），逐层 BFS、同层并发 4（`drive/providers/quark.ts:247`），每个目录至少一个 `file/sort` 请求（100 条一页）。
和上一轮的快照按网盘 id 对比（`diffSnapshot`），出新增 / 删除 / 改名 / 移动事件；一轮的事件全部处理完才把新快照写库（`commit`），
处理失败的变更从新快照里剔掉，下轮重发；一轮少了三成以上先压一轮。

**这些是对的，不动**：按 id 对比、事件排序（删、搬、建）、大比例删除阀门、commit 语义、某个根列不了只记 warning。

**问题**：

1. **代价和库的大小成正比，和变化量无关。** kuake 的 `/tv`（24 部剧，约 55 个目录）一轮约 55 个请求、30 秒；
   等待从上一轮结束算（`lib/polling.ts:12`），最短 300 秒（`sources/quark.ts:207`），一天约 1.4 万个请求，发现变化要 5～6 分钟。
   1000 个目录的库一轮 1000 多个请求，按默认每秒 2 个（`db/defaults.ts:14`）要 8 分钟以上，比间隔还长。
2. **走 `normal` 通道**（`quark/client.ts:177` 写死），和同步、转存、整理、浏览排同一条队；115 的监控走 `life`（`cloud-115/life.ts:187`）。
   每秒请求数是账号共用的，换通道只是不占 `normal` 的并发槽。
3. **没有变化也每轮整份重写快照**（`:293` 的 commit 对每个根都 `writeDriveSnapshot`）。
4. 嵌套的任务根（`/tv` 和 `/tv/动漫`）各列一遍（`:237` 只按完全相同去重）。指纹查询便宜以后这条无所谓，不处理。

## 真机实测（2026-10-14，kuake 账号）

### 只读（`/tv`，约 64 个请求）

- `file/sort` 的条目带 `include_items`（目录的直接子项数）、`updated_at`、`created_at`、`l_*`、`operated_at`、`update_view_at` 等。
  `include_items` 和列到的条数 48/48 一致；空目录不带这个字段（按 0）。
- **`update_view_at` / `operated_at` 是访问时间**：取直链、播放就变，并且往上冒（Foundation 09-23 被 OpenList 拉片、导演剪辑版播放）。
  **不能当变化信号**，否则看一集就会重列整条路径。
- 文件的 `created_at` 是分享源的原始时间，不是落进本盘的时间；文件 `updated_at` 随移动 / 改名变，下载不变。
- **`POST /file/info/path_list`** 回完整条目（带 `updated_at`、`include_items`，和列目录看到的一致），**一次最多 50 个路径**，
  51 个就报 `Bad Parameter: [fids size limit]`；不存在的路径直接不回。
- `_sort=updated_at:desc` 好用；`GET /member` 有 `use_capacity`。

### 写实验（根目录下建 `fp-lab-*`，做完整个删进回收站）

测试文件是从 `/tv/龙珠超 比鲁斯 (2026)/tvshow.nfo` 只读下载算哈希、用秒传（`upload/pre` + `update/hash`，md5 / sha1 小写十六进制，
`finish=true` 就成了，不传数据）在实验目录里生成的副本，原文件没动。三次实验目录 `/fp-lab-202610141601`、`/fp-lab2-202610141605`、
`/fp-lab2-202610141608` 都在回收站里。

| 操作 | 父目录 `updated_at` | 父目录 `include_items` | 条目自己的 `updated_at` |
|---|---|---|---|
| 新建目录、秒传文件进来 | 刷新 | +1 | — |
| 原地改名（文件、目录都试了） | 刷新 | 不变 | 刷新 |
| 移入（文件、目录） | 目标刷新 | 目标 +1 | 刷新 |
| 移出（文件、目录） | 源**不变** | 源 −1 | — |
| 删除（文件、目录） | **不变** | −1 | — |
| 孙辈的任何变化 | 不变 | 不变 | — |

- **节流**：父目录刷新之后约 5.5 秒内的变化不再刷新它（3.3 秒以内的都没刷新、5.4 秒以上的都刷新；按服务端时间临界在 5.35～5.64 秒之间）。
  实例：f3 连着改两次名，父目录只记到第一次；秒传 5 个文件，第 5 个没刷新。线上也见过（亿万地堡 Season 01 目录时间停在 01:31:04，
  E07 / E08 在 :06 / :08 落进来）。`include_items` 不受节流，每一步都立刻准。
- **可见性**：每一步动手后立刻读和 3 秒后读一致，没看到延迟（小目录；大批量转存没测）。4 个文件一次移动是同步完成的，20 ms 内落地。
- 点开头的目录列得出来、算进 `include_items`，20 秒后还在（和 09-16 记下的「会被藏起来」对不上，没复现）。

**结论**：指纹 = (`updated_at`, `include_items`) 能抓到直接子项的所有变化——新增、移入、改名靠 `updated_at`，删除、移出靠 `include_items`。
漏的只有「刷新后 5.5 秒内的改名」（条数不变、时间被节流吞掉），靠下面第 2 步的「刚变过的再列一次」兜住。

## 方案

### 1. 每轮的流程（每个根各走一遍）

**整棵列**（就是现在的做法，顺便把指纹记进快照）：没有快照；快照是旧格式（目录条目没有 `items`）；距上次整棵列超过 12 小时。

**否则增量**：

1. **取指纹**：快照里的根和所有目录，按 50 个一批调 `path_list`，得到每个目录的 `{id, updated_at, include_items}`。
   子目录超过 100 个的大平铺目录（电影库的 `movie/`）不逐个问子目录，改成直接列它：列一页 100 条，比 `path_list` 一批 50 个便宜一半，
   列出来的子目录条目本身就带指纹。
2. **判脏**，下面任何一条都要列：
   - 指纹和快照不同；
   - `path_list` 没回它，或者回的 id 和快照不同（改名、移走、被同名的顶替）——列它的父目录（父目录一般本来就脏了；父目录也找不到就再往上，
     根都找不到就和现在一样记 warning、跳过这个根、快照不动）；
   - **上一轮是因为刚变过才列的**（快照条目上的 `recheck`）：列的时候可能正处在节流窗口里、有改名被吞掉。下一轮离那次刷新至少隔了一个间隔
     （≥ 60 秒，远大于 5.5 秒），再列一次就一定看全了。这条规则不比较本机时间和夸克服务器时间，没有时钟偏差的问题。
3. **列脏目录**（绕开路径缓存），逐个子目录比：
   - 快照里没有这个 id → 新目录，整棵往下列；
   - id 在、路径变了（搬过来的、改了名的）→ 它自己的指纹（列表里带着）和快照一样就沿用快照里它的子树，只改路径前缀；
     不一样就列它。子树里的目录路径都变了，当轮按新路径补一次 `path_list`，有脏的接着列；
   - id 在、路径没变、指纹变了 → 列。
4. **拼新树**：从根往下走，列过的目录用新列表，没列的目录沿用快照里的子项（按 id 找回它在旧快照里的位置，搬过的改前缀）。
   同一个 id 在两处出现（旧父目录的 `include_items` 没跟上之类）只认列过的那处，旧父目录记脏下轮再看，打一条 debug。
   被因「变了」而列的目录标 `recheck`，因 `recheck` 而列、这次没变的清掉标记。
5. **往后全部照旧**：`diffSnapshot(prev, curr)` → 事件、排序、大比例删除阀门、commit 时才写快照、失败的变更从新快照里剔掉。
6. 这一轮一个目录都没列 → 不写快照、不出事件（现在每轮都整份重写）。

**首轮的 recheck**：首轮整棵列没有上一份可比，`updated_at` 离现在不到 10 分钟的目录标 `recheck`（一次性的，按本机时间估，时钟差几分钟也没事）。
定期整棵列时，和旧快照比指纹变了的目录标 `recheck`，和增量同一个道理。

**整棵列时顺便自检**：定期整棵列的结果和增量一路维护下来的快照对比，要是出了事件，说明增量漏了——这些事件照常处理，另外记一条 warning
（「整棵对比发现增量漏掉的 N 处变化」，带前几条路径）。夸克的规则哪天变了，靠它最先看出来。

### 2. 快照格式

- 目录条目（`SubtreeEntry`）加 `items?: number`（`include_items`）、`recheck?: true`；`modifiedAt` 本来就存的是 `updated_at`。
- 根自己的指纹和上次整棵列的时间：`drive_snapshots` 加一列 `meta`（JSON：`{ rootId, modifiedAt, items, recheck, fullAt }`），迁移 0022。
- 旧快照（目录没有 `items`）第一轮按整棵列处理，写回去就是新格式。
- 降级回旧版本：旧版的 drizzle 只选它认识的列、JSON 里多出来的字段不看，不受影响；再升上来时旧版写过的快照目录没有 `items`，按旧格式整棵列一次。

### 3. Provider 接口

- `DriveEntry` / `SubtreeEntry` 加 `items?: number`：目录的直接子项数。夸克解析 `include_items`（`RawFile` / `QuarkEntry` / `toEntry`），别家不填。
- `DriveProvider` 加可选的 `dirFingerprints?(paths, signal)` → `Map<path, { id, modifiedAt, items }>`：夸克用 `path_list` 50 个一批实现；
  没有它的网盘（OpenList、测试里不开指纹的 FakeDrive）快照源照旧整棵列。
- `listDir` 的 `opts` 加 `background?: true`：后台监控发的请求，夸克走 `life` 通道（`quarkRequest` 加通道参数，`quarkListDir` 透传）；别家忽略。
  `dirFingerprints` 也走 `life`。
- `quark/client.ts` 现有的 `quarkPathList` 给 `resolvePath` 用（两三个路径）；批量的另写一个分批的，或者把它改成内部 50 一批。

### 4. 节奏

- 最短间隔 300 → **60 秒**（`minIntervalSeconds`）。没变化的一轮只有 `ceil(目录数 / 50)` 个请求。
- 整棵列兜底每 **12 小时**一次（常量；它是安全网，不靠它发现变化）。
- 探测文案（`probe`）改成「没有事件流，每轮先比目录指纹、只列变了的目录（最短 60 秒一轮），每 12 小时整棵对比一次」。

| | 现在 | 改完 |
|---|---|---|
| kuake `/tv`（约 55 个目录）没变化的一轮 | 约 55 个请求、30 秒 | 2 个 |
| 一天 | 约 1.4 万（5.5 分钟一轮） | 约 2900（60 秒一轮）+ 两次整棵列 |
| 发现变化 | 5～6 分钟 | 1 分钟左右 |
| 1000 个目录没变化的一轮 | 1000 多个、8 分钟以上 | 20 个左右 |

### 5. 不做的（和原因）

- 不用 `update_view_at` / `operated_at`：访问时间，播放就变。
- 不用 `/member` 的容量做总闸：改名、移动不变；指纹已经够便宜。
- 不拿「最近文件」「回收站」当事件源：只覆盖新增或删除，还要另外反查路径。
- 嵌套的任务根各查各的：重叠部分多问几次指纹，不值得合并。
- 同步任务（全量）也是逐目录列，原则上也能借快照做增量；但同步是权威对照，这次不动。

### 6. 风险与兜底

- **夸克改了规则**（比如改名不再刷新父目录）：12 小时整棵列兜底，自检那条 warning 能让人看见。
- **`path_list` 认不出某个名字**（大小写、特殊字符；名字里带 `/` 的 walk 本来就跳过）：当「找不到」处理，列父目录就能找回来，
  只是每轮多列一次父目录；连续几轮都这样记一条 debug。
- **大批量异步落地**（几百个文件的转存）：落地期间父目录每 5.5 秒刷新一次，每轮都会列它，直到落完；最后一轮因为 `recheck` 再列一次，不会漏尾巴。
- **处理失败的变更**：`revertChange` 用的是完整的旧快照，增量拼出来的新树同样完整，剔掉 / 放回的逻辑不用改。

  - 现有十个场景在增量模式下再跑一遍，事件必须和整棵列一致；
  - 没变化：只调 `dirFingerprints`，不调 `listDir`，不写快照；
  - 季目录里加一集：只列那个季目录；删一集：靠条数发现；
  - 节流吞掉的改名：这一轮没看到、下一轮因 `recheck` 补上；

  - 旧格式快照：第一轮整棵列；12 小时到了整棵列，人为让增量漏一处，自检报 warning、事件照出。

**和方案不一样的地方**：

- 按原路径找不到的目录，标的不是直接父目录，而是**离它最近的、找得到的上级**（本来就没问指纹的大目录子目录也算停点）。
  只标直接父目录的话，剧目录改名时季目录找不到 → 把（也找不到的）剧目录本身标成要列 → 剧目录和根同一波列 → 存进去的是改名前的旧指纹，之后还得多列两轮。
- recheck 不比时间（方案里写的「listedAt 离 updated_at 不到 30 秒」）：**因为指纹变了 / 新出现才列的目录，下一轮无条件再列一次**；
  下一轮离那次刷新至少隔了一个间隔（≥ 60 秒，远大于 5.5 秒节流），一定看全。只有首轮整棵列没有上一份可比时按本机时间估（10 分钟以内的挂上）。
- 新增 `markDiverged`：要存的快照和这一轮实际看到的对不上（压下的大比例删除、处理失败剔掉 / 放回的变更），所在目录挂 recheck；
  否则那个目录指纹没变、下轮不会去列，留在快照里的东西再也不会被对比（反证：去掉它，「首轮 all 模式处理失败的新增」那条挂）。
- 同一波里上级列出来的子目录指纹不当它的「列之前的指纹」存（同一波并发，先后不确定）；用快照里的旧值，下轮对不上会再列，安全。

## 同步与监控的协调（2026-10-14 用户追问「任务开了定时执行怎么办」后定的）

**问题**：两边互不知道对方。全量同步拉到的远端清单可能比监控旧（大库光列目录就要几分钟，之后还要按清单补文件），
同步期间监控把网盘上的新变化落到本地，同步随后按旧清单把它改回去：
- 列完之后删了一集 → 同步照旧清单把 strm 建回来，留下一个指向已删文件的 strm；
- 列完之后改了名、监控先把本地改成新名 → 同步扫本地看到新名「多余」、旧名「缺」，删新建旧。
都要等下一次同步才纠正。改动前就有，但监控从 5 分钟一轮变成 1 分钟一轮，碰上的机会多得多；115 的监控是实时的，更容易碰上。

**做法：同步在跑的目录，监控照常发现变化，但先记下、不动本地；同步结束后按原来的先后补上。**
- 「忙」的范围：这个账号里正在同步（含启动阶段——拉远端目录树）的任务的 originPath。事件的新路径、旧路径任何一个和它交叠
  （相等、在它下面、或者是它的上级）就算在范围里。
- 记下：事件照常落库，状态 `deferred`（「同步任务在跑，等它跑完再处理」），不动本地。游标照常推进、夸克快照照常提交——事件已经在库里，不会丢。
- 补：每轮开始先把这个账号的 `deferred` 事件按记下的先后（rowid）逐条看：还在忙的范围里的继续等；否则和实时事件走同一条处理
  （整理自己的操作跳过、分派处理器、Emby 刷新、交给自动整理和复制到 OpenList）。
- 先后不乱：一轮里前面有事件还在等（或补失败）的路径，后面碰到同一处（交叠）的事件——不管是补的还是新来的——跟着等。
- 补失败：这一轮这一处先停，下一轮再试；连着三次还失败就标 failed（和实时处理失败一样）。次数记在内存里，重启从头数，最多多试三次。
- 同步一结束（跑完、起不来、被取消都算），登记表发 `task.finished`，监控对这个账号插一轮加急（`nudge`），不用等到下一轮。
- 去重：`deferred` 也算「已经接手」，115 重拉到同一条不会再处理一遍。留存清理（30 天）照常删：同步跑不了这么久，30 天还没补上的（监控停了一个月、账号删了）已经没意义，下一次全量同步会对齐。
- 重启：`deferred` 在库里，重启后第一轮就补（重启时没有在跑的同步）。
- 同步不等监控：同步拿到的远端清单一定不比监控旧，它覆盖掉的只会是更旧的状态，之后的变化监控下一轮照样补，先后都对。

**为什么不是「同步期间跳过那个根」**：那只适用于夸克这种快照来源（跳过不看，同步完再比就自然补上）；115 是事件流，跳不过去
（要知道事件落在哪个目录就得先解析路径，而解析会改路径缓存，回放时旧路径就对不上了），只能整个账号停下来等，
一个任务的长同步会把同账号别的任务的实时事件全拖住。记下再补对两种来源是同一个规则，来源本身一行不改。

**界面**：监控页账号行下面说「同步任务在跑（/tv）：先记下了 N 条变化，跑完自动补上」；事件列表「等同步」；结果列换成中文。
任务弹框的定时执行：这个账号开着监控时提示「网盘上的变化会自动同步，定时执行当兜底，每天一次就够」，定时比 6 小时还密时说明只会多跑全量。
